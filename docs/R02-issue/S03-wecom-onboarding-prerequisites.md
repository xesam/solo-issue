# S03 企微接入前置条件缺少自查清单，验证文件与部署前缀冲突

> 状态：待处理（不阻塞 0.0.1 内测）｜严重度：中｜记录日期：2026-10-23
> 2026-10-23 进展：`docs/08-deployment.md:5` 的反代表述已按 §4 第三条修正（接企微须前置反代、`WW_verify_*.txt` 由反代在根路径返回），§5 第二项验收已满足；§4 前两条（09 自查清单与 Nginx 示例）及与 S02 §5 的互链仍待办。

## 1. 现象

内测用户要使用企微免登录和消息推送，必须先满足一组企微平台侧的条件。`docs/09-wecom-setup.md` 写了这些条件，但分散在 §2 到 §4，没有一份在申请凭证前就能逐项确认的清单。其中"可信域名验证文件放到域名根目录"这一项与本项目的部署前缀冲突，文档没有给出做法。

## 2. 前置条件

| # | 条件 | 出处（`docs/09-wecom-setup.md`） | 常见卡点 |
|---|---|---|---|
| 1 | 企微超级管理员权限，用于创建自建应用 | §3 | 普通员工没有权限，需要管理员代为创建 |
| 2 | 公网可访问的部署域名 | §2 第 1 项 | 纯内网部署需要额外规划公网入口 |
| 3 | 可信域名归属验证：`WW_verify_xxx.txt` 放到域名根目录 | §4 | 见本文 §3 |
| 4 | 部署机固定出口 IP，加入"企业可信 IP" | §2 第 2 项、§4 | 动态出口 IP 变化后接口报错（错误码 60020） |
| 5 | 应用可见范围覆盖所有使用者 | §2 第 3 项 | 范围外的同事无法登录，也收不到通知 |

## 3. 验证文件与部署前缀冲突

- 应用挂在 `/solo-issue` 前缀下（`apps/web/src/lib/base-path.ts`），域名根路径不由应用响应（`docs/README.md` §2.2：裸根路径 404）；
- Next.js 配置 basePath 后，`public/` 下的静态文件也只在该前缀下提供；
- 因此 `https://<域名>/WW_verify_xxx.txt` 不能由应用本身返回，只能由前置反向代理提供。

结论：接入企微的部署实际需要前置反向代理。这与 `docs/08-deployment.md:5`"前端由 app 进程直接对外，无需额外反向代理"的表述不一致。

## 4. 处理方案

- `docs/09-wecom-setup.md` §2 开头加一份接入前自查清单（§2 表格的勾选版），让内测用户在申请凭证前逐项确认；
- `docs/09-wecom-setup.md` §4 补充验证文件的提供方式：由反向代理在根路径直接返回，附 Nginx 示例：

```nginx
location = /WW_verify_xxx.txt {
    alias /etc/nginx/wecom/WW_verify_xxx.txt;
}
```

- 修正 `docs/08-deployment.md:5`：直连部署只适用于不接企微的场景，接企微时需要前置反向代理；反向代理的转发头要求与 [S02](S02-trust-proxy-default.md) §5 互链。

## 5. 验收标准

- 一位没有参与开发的内测用户按 `docs/09-wecom-setup.md` 从零完成接入，记录卡点并补进文档；
- `docs/08-deployment.md` 与 `docs/09-wecom-setup.md` 对"是否需要反向代理"的表述一致。

## 6. 待确认

- 企微对可信域名的其他平台要求（如域名主体与企业主体一致、ICP 备案）本文未核实，以企微管理后台当前的提示为准，确认后补进 §2 清单。
